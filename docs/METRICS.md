# TDD スキル評価指標リファレンス

各指標の意味・計算方法・判定基準をまとめる。指標の優先度・ベースライン値は [ROADMAP.md](./ROADMAP.md) を、問題の詳細は [PROBLEMS.md](./PROBLEMS.md) を参照。

---

## Tier 1: コア指標（毎イテレーション計測・長期追跡）

### `red_authenticity_rate` — RED の真正性

**関連問題**: P11

**意味**: RED フェーズで書かれたテストが、書いた時点で本当に失敗していたかを測る。  
TDD の RED→GREEN の因果関係が成立しているかの基本チェック。

**計算式**:
```
FAIL または build error を記録した RED スナップ数 ÷ 総 RED スナップ数
```

**判定方法**: `cycle-N-red/test_output.txt` に `FAIL` または build error が含まれるか。

---

### `phase_write_order_rate` — PHASE 書き込み順序の正確性

**関連問題**: P1

**意味**: `.tdd/PHASE` への書き込みがコミットより前に行われているかを測る。  
スナップショットが「そのフェーズで何を変更したか」を正確に記録するための前提条件。  
この値が低いと、GREEN/REFACTOR スナップショットに実装差分が残らず、他の指標の計測精度が落ちる。

**計算式**:
```
git_diff に .go 変更を含む (GREEN + REFACTOR) スナップ数 ÷ 総 (GREEN + REFACTOR) スナップ数
```
**備考**: iteration-2 時点では 5.6% と最低。他の指標の信頼性にも影響するため最優先課題。

---

### `red_preceded_green_rate` — GREEN の前に RED があるか

**関連問題**: P4

**意味**: すべての GREEN が直前に対応する RED を踏んでいるかを測る。  
Triangulation（一般化）の途中で RED をスキップして GREEN→GREEN と進むパターンを検出する。

**計算式**:
```
直前に同サイクルの RED がある GREEN 数 ÷ 総 GREEN 数（history.log ベース）
```
---

### `green_phase_purity` — GREEN フェーズの純粋性

**関連問題**: P3

**意味**: GREEN フェーズで余分なテスト追加が行われていないかを測る。  
テストの追加は RED フェーズの責務であり、GREEN で追加するとチートが生まれやすくなる（P7 参照）。

**計算式**:
```
テスト追加のなかった GREEN スナップ数 ÷ 総 GREEN スナップ数
```
---

### `refactor_noop_rate` — 空 REFACTOR コミット率

**関連問題**: P2

**意味**: リファクタリング不要時に空コミットを作っていないかを測る。  
改善箇所がなければ次の RED へ進むべきであり、空コミットは git 履歴を汚染する。

**計算式**:
```
コード変更のない refactor: コミット数 ÷ 全 refactor: コミット数
```


---

### `test_first_rate` — テストファースト率

**関連問題**: P7

**意味**: すべてのテスト関数が、対応する実装より先に RED になった経験を持つかを測る。  
実装を後追いするテスト（一度も RED にならないテスト）はチートであり、TDD の根本原則に反する。

**計算式**:
```
RED フェーズで FAIL したことのあるテスト関数数 ÷ 総テスト関数数
```

## Tier 2: 補助指標（余裕があれば計測）

### `language_idiom_rate` — 言語イディオム採用率

**関連問題**: P6

**意味**: テストコードが対象言語の推奨イディオムに従っているかを測る。  
Go の場合は Table-Driven Test スタイルが推奨される。

**判定方法**: pass / fail（イディオムを採用しているか否か）

**前提条件**: 言語別のルールが `~/.claude/rules/` に定義されていること。

**理想値**: 100%（全テストファイルがイディオムに準拠）

---

### `fake_it_rate` — Fake It 採用率

**関連問題**: P5

**意味**: GREEN フェーズで、テスト件数が少ない段階に見合った最小実装（Fake It）が使われているかを測る。  
1件目のテストから汎用実装（Obvious Implementation）を書くと、テストが検証していない動作まで実装が先行するリスクがある。

**判定方法**: LLM 採点（「最小限の実装か否か」を判断）

**前提条件**: P1 が解決され GREEN スナップショットに実装差分が残るようになっていること。
---

## Tier 3: 効率指標

### `tokens_per_cycle` — サイクルあたりトークン数

**関連問題**: P8

**意味**: 1 TDD サイクル（RED→GREEN→REFACTOR）を回すのに消費したトークン数の平均。  
スキルの効率改善の効果測定に使う。

**計算式**:
```
総トークン数 ÷ 総サイクル数
```

---

### `tool_calls_per_cycle` — サイクルあたりツール呼び出し数

**関連問題**: P8

**意味**: 1 サイクルあたりのツール呼び出し回数の平均。  
過剰なファイル読み書きや不要な確認ステップがないかを見る効率指標。

**計算式**:
```
総ツール呼び出し数 ÷ 総サイクル数
```
